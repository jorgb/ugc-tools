
### 2026-09-18 — cross-checked against an independent RE project

[TuscanPL/SparkyMK2](https://github.com/TuscanPL/SparkyMK2) is a clean-room
reverse-engineering project for the same device, built from USB captures of
the official app plus its own pattern-file export tests. Its
[`docs/re/04-patterns.md`](https://github.com/TuscanPL/SparkyMK2/blob/main/docs/re/04-patterns.md)
covers exactly this file format independently. Comparing against everything
found below:

**Tick math confirmed, not contradicted.** SparkyMK2 states "480 ticks per
quarter note" and that every pattern file in their export totalled 7680
ticks = 4 bars of 4/4. That's the *same* 480-ticks-per-quarter as this
file's own finding (1920 ticks per bar ÷ 4 beats = 480/beat) — the
"1920" and "7680" numbers aren't in conflict, they're just a 1-bar test
pattern here vs. a 4-bar one there (1920 × 4 = 7680).

**Pad-ID decoding confirmed byte-for-byte.** SparkyMK2 independently
describes byte 1 as "note on pad `0x2F` + bank-within-group × 16 +
(pad − 1)" with byte 2's low nibble selecting "0 = banks A–E, 1 = banks
F–J" — this is exactly `sp404.ptn.PadID`'s logic and its `0x2f`–`0x7e`
range check, arrived at completely independently (they reverse-engineered
the *live USB protocol*, not this file format). One robustness note: they
say "low nibble," implying the rest of the byte could carry other bits;
`PadID` currently requires `pad_toggle` to be exactly `0x00` or `0x01` and
raises otherwise — masking with `& 0x0F` first would be a touch more
defensive, though no evidence has turned up of the upper nibble ever being
non-zero.

**That "no evidence yet" turned into a real crash on 2026-09-18.** Running
the converter against a real, older project export
(`testing/SP404mk2/playy/`, a 101-pad/16-sequence project — much richer
than this repo's earlier single-kick fixtures) hit
`PTN00001.BIN`/`PTN00081.BIN` records with byte 2 = `0x40` (e.g.
`10 3B 40 00 14 40 2C 00`), which `PadID` rejected outright. Fixed exactly
as anticipated above: `PadID` now masks `pad_toggle & 0x0F` before checking
it's `0x00`/`0x01`, so the documented-but-previously-unhandled `0x40` bit
is ignored rather than crashing the converter. Regression test:
`tests/test_ptn.py::test_pad_id_ignores_unknown_high_bits`.

**Also found against that same real project: the chromatic-pitch baseline
assumption (§3.2 below, "0x8D is most common") doesn't hold universally.**
Every single note event across all 16 sequences in that project uses byte
3 = `0x00`, never `0x8D`. Per SparkyMK2's own description quoted below,
`0x00` *is* documented as "plain note" (i.e. explicitly not chromatic) —
so this isn't a new/contradictory finding, just a reminder that "0x8D is
most common" was true only for this repo's earlier, narrower test
fixtures. `convert/xpj/mapping.py`'s `is_baseline_chromatic_pitch()` now
treats both `0x00` and `0x8D` as "no pitch shift, don't warn," instead of
only `0x8D`.

**Record types: 0x8C and 0x8E are not just "fillers" — this likely answers
the EXT-IN automation question below.** SparkyMK2 documents record type
byte 1 more precisely than "any value ≥ 0x80 means no pad": `0x8C` is
specifically the end-of-events marker (the next record is the trailer —
matches this file's own finding), `0x8E` is specifically a **control
change** event (byte 2 = MIDI channel, byte 5 = controller, byte 6 =
value), and *only other* values ≥ 0x80 are pure time-filler with no
payload. This is almost certainly the "EXT-IN automation" mechanism this
file's own TODO list has been asking about.

This matters for `sp404/ptn.py`: it currently treats *any* record with
`buf[1] & 0x80` set as "no pad information" and (per the planned extension
in `convert/xpj/DESIGN.md` §3.2) would fold all of those into pure tick
filler and discard them — which would silently swallow `0x8E` control-change
payloads along with genuine fillers. Worth special-casing `0x8C` (stop,
trailer follows — already effectively handled today since the last 16
bytes are sliced off as the footer) and `0x8E` (extract channel/controller/
value) before treating everything else ≥ 0x80 as filler.

**Applied 2026-09-18** — `PatternEvent` now special-cases `0x8E` before the
general `& 0x80` filler check, exposing `midi_channel`/`controller`/
`controller_value` (`None` for every other record type). `0x8C` still isn't
special-cased inside `PatternEvent` itself since `Pattern._read` already
slices the last 16 bytes off as the footer before any 8-byte record ever
reaches `PatternEvent`, so it never sees a `0x8C` record in practice. The
converter side (mapping these to an actual XPJ automation event) is still
unimplemented — see `convert/xpj/DESIGN.md` §3.2.

**Byte 3 (chromatic pitch) is a flag+value, not a raw offset.** SparkyMK2:
"0 = plain note. Otherwise a pitched note: bit 7 is a flag and bits 0–6 a
value; `0x8D` is most common, probably the original pitch." This lines up
with every hex dump in this file — byte 3 is `0x8D` in literally every
example captured so far, which is exactly why "Chromatic pitch?" is still
unresolved here: none of the test patterns captured so far happen to vary
it away from that baseline value.

**New finding: bytes 4 and 5 are two separate velocities, not one.**
SparkyMK2: byte 4 = note-on velocity, byte 5 = **note-off velocity**
(constant `64` in every file they examined). This file's own very first hex
dump independently confirms the second half: `... 5A 40 77 00` has byte 5 =
`0x40` = 64, an exact match, even though this file never previously
identified byte 5 as anything (the "Notes from NearTao" table below leaves
`xxx5` blank). Byte 4 in that same example is `0x5A` = 90 — not the fixed
127 SparkyMK2 says they saw "in every file," which just reflects that this
file's test pattern deliberately varies pad velocity (see the "A02 = PAD
velocity" entry further down) while SparkyMK2's sample set apparently
didn't. `sp404.ptn.PatternEvent.velocity` currently only reads byte 4
(note-on); byte 5 (note-off velocity) isn't exposed at all.

**Trailer bytes refined — partly confirms, partly corrects, this file's own
findings.** SparkyMK2's trailer layout: byte 0 = bars count, byte 4 = time
signature (0=4/4, 1=1/4, 2=2/4, 3=3/4, 4=5/4, 5=6/4, 6=7/4), byte 7 = must
be non-zero. Byte 0 and byte 7 match this file's own findings exactly
(`x01` for a 1-bar pattern; `x01` non-zero sentinel). **Byte 4 (time
signature) is new** — not previously identified here.

For trailer bytes 5–6, though, **this file's own findings look more
accurate than SparkyMK2's**: SparkyMK2 calls both "`80`, `04` in every file;
unused by the app," but the "Notes from NearTao" section below already
documents byte 6 varying between `x01` (1 bar) and `x40` (64 bars) as
"loop end" — directly contradicting "always `0x04`." The likely explanation
is that SparkyMK2's own test files all happened to share one loop-end
value, making it look constant in their smaller sample. Trust this file's
"loop start / loop end" reading for trailer bytes 5–6 over the external
source.

**New file: `PTN/PATTERNCHAIN_00.CHN`.** SparkyMK2 documents an XML file
alongside the `PTN/` folder listing the project's pattern-chain order and
repeat mode (pattern numbers in chain order, not names). It isn't present
in `testing/SP404mk2/pad-sequencer/2026-04-08/` — worth checking whether a
fresh export includes it, since the `convert/xpj/DESIGN.md` open question
about recovering human-readable sequence names would still need something
else (this file only carries chain order, not names).

**Bonus, relevant to `convert/xpj/DESIGN.md`'s pad→note mapping decision
(not something to fix here, just worth cross-referencing):** SparkyMK2
documents the official app's *own* SMF-export note mapping as
`note = 36 + T[pad − 1]` with `T = [12,13,14,15,8,9,10,11,4,5,6,7,0,1,2,3]`
— a reversed-4-block mapping (pads 13–16 → notes 36–39, pads 9–12 → 40–43,
pads 5–8 → 44–47, pads 1–4 → 48–51), not a simple sequential one. The XPJ
design doc currently uses a simpler sequential 37–52 mapping instead; that
remains a valid choice since the mapping is fully self-describing in XPJ
(`padNoteMap`), but adopting Roland's own scheme would make the converted
project's note numbers match what you'd get from the SP404's own MIDI
export feature, for whoever finds that useful to cross-check against.

Since we have a grid of 1920 ticks, and we have two notes starting at offset 0x00, and we have one offset at the end
that is 0x87, we can try 1920 - 0x87 = 1785, since we have 7 entries with 0xff, and 1785/7 = 255 (0xff) it seems that
the offset(s) above 127 with no pad info are there to count the ticks in a 1920 counter for our sequence.

This means every grid we see will start a counter at 0, up to 1920, and we can decipher what notes fall where, and for
entries with a pad entry of 0x80 are fillers.
